# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

NeoNorton is a retro, keyboard-driven text editor inspired by the classic Norton Editor of the 1980s, written in Java 17 against the [Lanterna](https://github.com/mabe02/lanterna) terminal-UI library. It's a nostalgic/learning project, not production software — favor simplicity and fidelity to the retro feel over modern editor conventions. It intentionally targets plain text and source code, not arbitrary binary files (confirmed with the user) — don't treat that as a gap to fill.

## Build, run, and package

```bat
mvn package
run.bat [filename]
```
```sh
mvn package
./run.sh [filename]
```

- `mvn package` compiles and (via the shade plugin) produces `target/retro-text-editor-1.0-SNAPSHOT-shaded.jar`, an executable fat jar with `br.com.demersonpolli.neonorton.Main` as the entry point.
- `run.bat` (Windows) launches that shaded jar with `javaw`; `run.sh` (macOS/Linux, `chmod +x` already set in git via `.gitattributes`) launches it with `java`. Both forward all arguments to the app and detach rather than blocking the invoking shell/console, and both exit with a clear message instead of running `java`/`javaw` at all if the jar hasn't been built yet.
- There is no test suite and no linter configured in this repo. `apache-maven/` is gitignored and not actually present in a fresh checkout — if `mvn` isn't on PATH, compile directly with `javac -encoding UTF-8` against a downloaded `lanterna-3.1.1.jar` (Maven Central), matching what the CI-less workflow in this repo's history actually did.
- Target OS is Windows: the app opens a `SwingTerminalFrame` (a Swing window emulating a terminal), so it will not run headless.
- **Use a stable LTS JDK (17 or 21) to build and run, not a bleeding-edge/non-LTS build.** A real compatibility bug was found empirically: under at least one non-LTS JDK, Lanterna's CJK-width-detection code (`TerminalTextUtils.isCharCJK` → `Character.UnicodeBlock.of()`) hangs at ~100% CPU on the splash screen instead of ever showing a window. Not a bug in this codebase; a JDK/Lanterna interaction. If `java -version`/`javac -version` on PATH resolve to something unusual, get a JDK 17/21 install instead of debugging further here.

## Architecture

The whole app is a sequence of full-screen `AppScreen` implementations driven from `Main`, sharing one Lanterna `MultiWindowTextGUI`/`Screen`:

- `Main` parses CLI arguments (`+LINE`, `INPUT`/`OUTPUT` paths, `/DA`/`/DB`/`/DC` or long-form `--line`/`--input`/`--output`/`--display`/`--safe`/`--encoding`), loads a saved `EditorConfig` (see below) to pick the terminal's cursor style and font size *before* constructing the `SwingTerminalFrame` (both are immutable once the frame exists — no live-update API), then shows `SplashScreen` (only if no `INPUT` was given) to collect a filename, then shows `EditorScreen`.
- `AppScreen` is a one-method interface (`show(MultiWindowTextGUI gui)`); `SplashScreen`, `HelpScreen`, `StatusScreen`, and `EditorScreen` all implement it. Each screen owns its own `screen.readInput()` loop and draws directly via `TextGraphics` (Lanterna's immediate-mode drawing, not its widget/component system) — there are no reusable UI widgets.
- `StatusBar` is the one shared UI helper: a row of label/column pairs rendered in reverse video. `EditorScreen` keeps six `StatusBar` instances (one normal + one overlay per F3–F7 mode) and swaps which one is rendered depending on the active mode.
- `HelpScreen` (F1) is paged: a `String[][] PAGES` constant, one page per command family, navigated with PgUp/PgDn or arrow keys. Keep it in sync when adding or changing a command — it's meant to be the in-app reference, separate from `README.md`.
- `PdfWriter` is a small, dependency-free PDF generator (F7's "print" target — see below) — plain text only, Courier/Base-14 font, no external library.
- `ShellLauncher` opens a real OS shell window per platform (F9) — `cmd.exe` on Windows, `Terminal.app` via `osascript` on macOS, the first available terminal emulator on Linux. Only the Windows path has actually been exercised; the environment this was built in can't reliably launch/observe console windows at all (confirmed: even a bare `cmd.exe` shows no window there, while AWT/Swing windows work fine — an environment limitation, not a code issue), so treat macOS/Linux as reviewed-against-documented-behavior, not proven.
- `EditorConfig` is a plain data holder + `load()`/`save()` against `~/.neonorton/config.properties` (F5 S). `EditorScreen.applyConfig()` is its read-side counterpart, called once at startup before CLI flags (e.g. `/DA`) are applied, so an explicit flag always wins over a saved default.

### EditorScreen — the core of the app

`EditorScreen` (~2500 lines) is a single class holding the whole document model, cursor state, and all editing/command logic — there's no separate model/view/controller split. Key things to know before editing it:

- **Document model**: `List<StringBuilder> lines`, plain UTF-8 text — deliberately not a byte/binary model. Cursor is `(cursorRow, cursorCol)`, always a *document* character index; `scrollRow` tracks the top visible line. Tabs are stored as literal `'\t'` characters but rendered expanded (`expandTabsForDisplay()`), so document columns and screen columns diverge on any line containing a tab — anything that maps a document position to a screen position (cursor placement, block-highlight boundaries) goes through `docColToScreenCol()`, not a raw `cursorCol`/marker-column comparison.
- **Main loop** (`show`): reads one `KeyStroke` at a time. Function keys F1–F9 and Tab (in split mode) are handled directly in `show()`'s loop; everything else goes through `handleKey`, a big switch on `KeyType` handling navigation, insertion, deletion, Tab (per `tabMode`), and Ctrl/Alt chord shortcuts (word delete, line delete, case toggle, undo, search, Ctrl-P).
- **Split-pane via field-swapping**: rather than maintaining two parallel editor objects, there is exactly one set of "live" fields (`lines`, `cursorRow/Col`, `scrollRow`, `insertMode`, `activeFileName`, `lineEnding`, block markers, the undo stack) plus a parallel `*2` set for the inactive pane. `swapActivePaneData()` swaps the live fields with the `*2` fields. The pattern used throughout `show()` is: if pane 2 is active, swap in its data, run the normal single-pane logic against the "live" fields, then swap back. This means most editing/command methods are written as if there's only ever one pane, and split-pane support is layered on entirely at the call sites in `show()`. When adding a new piece of per-document state, add it to both the swap and to `closeSplitPane()`/`enterSplitMode()`'s reset logic — it's easy to leave a new field un-swapped and get cross-pane bleed (this happened once with the undo stack before it was fixed).
- **Block operations** (F4) mark a region with `markerBeginRow/Col` and `markerEndRow/Col` (`-1` row means "no marker"). `normalizeMarkers()`/`hasFullMarkers()` are the guards other block methods rely on before acting. `extractBlockContent`/`insertBlockAt`/`deleteBlockContent` are the primitives block ops build on; search & replace has its own parallel primitives (`deleteRange`/`insertTextAt`/`replaceMatch`) rather than reusing the block ones, specifically so a search/replace operation can never clobber the user's actual F4 block selection.
- **Undo** is a real multi-level stack (`undoStack`, a `Deque<UndoEntry>` capped at `UNDO_STACK_LIMIT`, one per pane like other per-pane state). Each `UndoEntry` is a full-buffer snapshot, not a per-line diff — a deliberate simplicity/memory tradeoff. `saveUndo()` pushes a checkpoint and must be called before any mutation; `insertChar()` (shared by plain typing and Ctrl-P) coalesces a run of consecutive plain keystrokes into a single checkpoint via its `coalesce` flag so undoing a typed sentence is one `Ctrl-U`, not one per character — any other key breaks the run. When adding a new mutating command, call `saveUndo()` (after any early-return no-op guards, so a no-op keypress doesn't waste a stack slot) — it's easy to add a new `lines.` mutation and forget this.
- **Search & replace** (`Alt-F`/`Ctrl-F`/`Alt-C`/`Ctrl-C`) supports literal multi-line terms (`Ctrl-Return` embeds a `'\n'`) matched against real line boundaries — see `matchAt()`/`findForward()`/`findReverse()`. Pressing the same find direction twice (once a term is "pending") switches from find to a Y/N/*/Space replace loop; `forwardFindPending`/`reverseFindPending` track that state per direction.
- **File I/O**: `saveFile()` writes to a temp file in the same directory and atomically renames it over the target (falling back to a plain replace if the filesystem can't do atomic renames), and preserves the original file's CRLF-vs-LF style (`lineEnding`, per-pane). Still plain UTF-8 text, not byte-safe/binary (see the scope note above) — but loading is a real incremental `FileSource` now, not a stub: `loadFilePrefix()` reads a file in `INITIAL_LOAD_BYTES`/`CHUNK_LOAD_BYTES`-sized pieces (trimmed back to the last line boundary — splitting exactly on a `'\n'` byte is always UTF-8-safe), `unreadOffset`/`fileSize` (per pane) track how much is left, and F3 L pulls in the next chunk. `saveFile()` carries forward whatever was never loaded — read straight from disk and appended after what's written from memory, with the boundary newline between them explicitly restored (lines are joined *between* each other, not after the last one, so this is easy to get wrong — it was, once, caught by the reflection test that exercises a multi-chunk file's save path) — so saving before loading everything can never truncate or corrupt the file.
- Screen redraws go through `redraw()` → `drawTextPane()` (draws the buffer, handling scroll, tab expansion, and block-marker highlighting) → `updateStatusBar()`. Any change to cursor/scroll/mode state should be followed by a call into this redraw path (as the existing key handlers do) rather than drawn ad hoc.

Full key bindings and per-mode command tables (F3 file ops, F4 block ops, F5 format ops, F6 misc ops, F7 print/PDF ops, search & replace, split-pane behavior) are documented in `README.md` and in the app's own paged `F1` help (`HelpScreen.PAGES`) — treat both as the source of truth for user-facing behavior when changing key handling, and keep them in sync with each other.
